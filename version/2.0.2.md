## 问题原因
- 当前项目在开发态由 `server.ts` 同时承接页面与 `/api/*` 请求，因此前端直接写相对路径 `/api/...` 可以正常工作。
- 但生产环境如果只把 `dist/` 静态文件部署到 Nginx，而没有运行 Node/Express 后端，或没有把 `/api` 反向代理到后端服务，那么浏览器访问 `/api/login`、`/api/guest-login`、`/api/posts` 时会直接命中 Nginx 静态站点，最终返回 `404`。
- 这不是单纯登录页的问题，而是整站前端数据请求在生产环境的地址解析缺少部署层适配。

## 关键改动
- 新增 `src/lib/api.ts`：
  - 提供 `resolveApiUrl()`，统一拼接前端请求地址。
  - 提供 `resolveAssetUrl()`，统一处理上传图片等资源地址。
  - 支持通过 `VITE_KUROMI_API_BASE_URL` 配置生产环境 API 基址。
- 将以下模块中的硬编码 `fetch("/api/...")` 改为统一走 `resolveApiUrl()`：
  - 登录注册
  - 访客留言
  - 帖子列表/详情/评论
  - 帖子编辑/发布/删除
  - 标签页数据拉取
  - 编辑器图片上传
- 图片上传成功后，前端现在会对返回的图片地址做一次 `resolveAssetUrl()` 处理，避免前后端分离部署时新上传图片仍然指向错误站点。

## 生产部署说明
- 推荐方案一：Nginx 同域反代
  - 前端静态资源继续由 Nginx 提供。
  - `/api/` 和 `/uploads/` 反代到运行中的 `server.ts` 服务。
  - 这种情况下无需设置 `VITE_KUROMI_API_BASE_URL`，前端默认同源访问即可。
- 推荐方案二：前后端分离域名/端口
  - 构建前设置 `VITE_KUROMI_API_BASE_URL`，例如：
  - `VITE_KUROMI_API_BASE_URL=https://your-api.example.com`
  - 然后重新执行 `npm run build`。
  - 注意：如果前后端不同源，还需要你在 Nginx 或 Node 层自行处理跨域策略；本次代码未主动放开跨域。

## Nginx 示例
```nginx
server {
    listen 80;
    server_name your-domain.example.com;

    root /var/www/kuromi/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /uploads/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
